# 万能接口框架规范契约 v1

文档状态：Stage 1 冻结规范
版本：1.0
日期：2026-11-04
适用范围：中枢、接口、编排者、执行者、核验者与负责人之间的控制面和数据面协作

本契约使用“必须”“不得”“应当”“可以”区分规范强度。机器可读约束以 `schemas/envelope.schema.json`、`schemas/verdict.schema.json` 和 `schemas/verdict-aliases.json` 为准；本文件解释这些约束的语义和边界。

## 1. 设计边界

本框架分为控制面和数据面。

- 控制面负责任务登记、路由、生命周期、租约、裁定和审批；控制面记录必须可重放、可审计、账实一致。
- 数据面负责连接、事件、结果和产物传输；数据面可以最终一致，但必须提供持久暂存、去重和补投。
- 数据面故障只能影响传输快慢，不得冻结或改写控制面事实。
- 业务流转由事件驱动。低频序号核对只用于发现缺号，不得成为主链路轮询。
- 执行者只能声明已执行的动作；任务是否通过由裁定记录决定。执行终态不等于任务通过。
- 同一 `resource_key` 同一时间只能有一个活动任务。任务、事件、结果和裁定都以中枢记录为事实来源。

## 2. 角色与信任边界

- **中枢**持有任务登记、追加式事件账本、租约代次、审批记录和裁定记录，并负责鉴权与路由。
- **接口**代表一个执行端点连接中枢，向执行者传递控制信令，并持久化发件箱、结果与操作账。
- **编排者**提交任务、组织核验并请求裁定，不能把自己对结果的声明当作裁定。
- **执行者**执行任务并提交声明、事件与结果指针。
- **核验者**必须未参与该次执行，负责确定性检查、独立核验和实物回读。
- **负责人**只处理必须由其决定的高影响事项。其决定经中枢验证、绑定并记录后才形成审批凭据。

席位之间不得建立绕过中枢的业务信道。任何无法由中枢记录关联的声明、结果或副作用都不作为控制面事实。

## 3. 任务信封

每次提交都使用一个完整的任务信封。信封是控制面对象，不是执行日志。

| 字段 | 必填 | 约束与语义 |
|---|---:|---|
| `contract_version` | 是 | 固定为 `1.0`。 |
| `envelope_id` | 是 | 信封版本标识；每次新提交生成新值，UUID。 |
| `task_id` | 是 | 全局唯一任务标识，UUID。重投同一任务时保持不变。 |
| `idempotency_key` | 是 | 编排者在同一提交主体范围内生成的稳定键，8–128 个 URL 安全字符。 |
| `target` | 是 | `interface_id` 或 `capability` 二选一；两者同时出现视为不合法。 |
| `instruction` | 是 | 原样传递的纯文本任务正文；接口不得二次拼接或改写。 |
| `skill_ref` | 否 | `null`，或含 `name` 与 `version` 的手册引用。接口只按引用读取已授权手册。 |
| `resource_key` | 否 | `null` 或稳定的资源作用域键；同键任务串行。 |
| `params` | 否 | `null` 或结构化参数对象。不得放入密钥、口令或明文凭据。 |
| `attachments` | 否 | 产物或输入指针数组；每项至少有 `uri`、`sha256`、`bytes`、`media_type`。 |
| `timeout_s` | 是 | 任务执行期限，正整数秒；与连接超时、事件确认超时彼此独立。 |
| `cls` | 是 | `readonly`、`reversible` 或 `external`。`external` 表示动作可影响系统外部。 |
| `priority` | 否 | `high`、`standard` 或 `low`；默认 `standard`。优先级不改变围栏与审批规则。 |
| `approval` | 条件必填 | `cls=external` 时必须提供有效审批凭据；其余场景为 `null` 或缺省。 |
| `created_by` | 是 | 通用角色称谓，不得填写个人身份或凭据。 |
| `created_at` | 是 | RFC 3339 日期时间。 |
| `trace_id` | 是 | 跨任务追踪标识，UUID。 |

信封序列化后不得超过 262,144 字节。大内容必须通过附件指针引用。中枢在入队前至少校验：必填字段、二选一目标、字段类型、正文完整性、附件哈希、`cls` 与目标动作的明显一致性，以及外部动作的审批绑定。

同一提交主体使用同一 `idempotency_key` 重试时：

1. 若规范化后的任务语义摘要相同，返回既有 `task_id`，不得创建第二个任务。
2. 若语义摘要不同，拒绝并返回幂等冲突，不得覆盖既有信封。
3. `task_id` 与 `idempotency_key` 必须分别唯一；两者都不得复用于语义不同的任务。

## 4. 生命周期状态机

控制面状态固定为：

| 状态 | 含义 |
|---|---|
| `QUEUED` | 已校验并入账，等待派发。 |
| `DISPATCHED` | 已交给某接口，尚未确认认领。 |
| `CLAIMED` | 当前接口持有匹配租约与围栏，任务尚未开始执行。 |
| `RUNNING` | 执行者已经开始工作。 |
| `SUCCEEDED` | 执行者已提交完成声明与可核结果指针；等待裁定。 |
| `FAILED` | 执行失败，且该次尝试不再继续。 |
| `TIMED_OUT` | 任务期限已过，且该次尝试不再继续。 |
| `CANCELLED` | 任务被有效取消。 |

允许的主要转移为：

```text
QUEUED -> DISPATCHED -> CLAIMED -> RUNNING -> SUCCEEDED
                                         \-> FAILED
                                         \-> TIMED_OUT
QUEUED | DISPATCHED | CLAIMED | RUNNING -> CANCELLED
CLAIMED | RUNNING -> QUEUED     (租约回收且有界重试)
```

规则如下：

- `SUCCEEDED` 只表示执行声明已交，不表示任务通过；没有裁定记录时按未核处理。
- `FAILED`、`TIMED_OUT`、`CANCELLED` 和 `SUCCEEDED` 是执行终态。执行终态不得改回活动态。
- 可重试失败不得复活旧任务；编排者决定重派时创建新任务并保留全部历史引用。
- 不可重试失败、毒消息和重试耗尽进入死信记录；原信封、事件、结果原因码与裁定关联必须保留。
- 每次状态变化都追加“前态、后态、时间、触发事件、操作者、尝试号、围栏代次、原因码、证据引用”。当前状态由账本重放得出。
- 连接超时、事件确认超时和任务期限是三套独立判定。任何一层超时不得推导出另一层成功或失败。

## 5. 事件与补投

生命周期事件类型固定为：

1. `accepted`：中枢确认任务已登记。
2. `claimed`：接口以当前围栏认领任务。
3. `progress`：执行者报告有实质进展。
4. `heartbeat`：接口证明连接和租约仍存活。
5. `result_ready`：结果已持久落盘，可以按指针核验。
6. `completed`：执行者提交完成声明。
7. `failed`：执行失败，必须带机器可读原因码及 `retryable` / `non_retryable` 分类。
8. `cancelled`：取消已生效。

所有事件至少包含 `event_id`、`task_id`、`seq`、`attempt`、`fence`、`occurred_at`、`sender_role`、`payload`。

- `seq` 在同一 `task_id` 内严格单调递增；重投保持原值。
- 接收端按 `(task_id, seq)` 去重；执行端还必须使用任务幂等键和尝试围栏，防止至少一次投递引发重复执行。
- `heartbeat` 只续租、不代表有业务进展。长任务只有心跳而长期没有 `progress` 或结果时，按假活处理。
- 接口离线期间产生的事件和结果必须先进入持久发件箱。重连后按 `seq` 顺序补投，补投完成前不得领取新任务。
- 中枢必须以任务账本核对事件序号。发现缺号时请求补投或启动低频对账；对账频率由实现记录并保持低频。
- 事件解析失败不得造成无限重试。必须保留原始消息指纹、隔离到死信并产生审计事件。

## 6. 租约与围栏

任务从 `DISPATCHED` 进入 `CLAIMED` 时，中枢原子地签发：

- `lease_id`：本次认领的唯一标识。
- `lease_expires_at`：当前租约的绝对到期时间。
- `attempt`：同一任务内的尝试号，从 1 开始。
- `fence`：同一任务内严格单调递增的围栏代次；每次新认领必须增大。

接口的所有续租、进度、结果和完成事件都必须携带当前 `attempt` 与 `fence`。中枢只接受与当前租约完全匹配的写入。

旧围栏、旧尝试、过期租约或错误持有者的消息必须拒绝并追加审计事件；不得覆盖新持有者的结果或状态。租约可以随有效的 `heartbeat`、`progress` 续期，但续租不得跳过序号或修改围栏。

租约到期后：

- `CLAIMED` 或 `RUNNING` 且副作用可判定为未发生时，可以经过实现声明的宽限期回收为 `QUEUED`，在新尝试中签发更大的围栏。
- `external` 任务若无法证明副作用未发生，必须保留在人工处置状态并标记“副作用未知”，不得自动重派。
- 回收、宽限、失败分流和人工处置都必须入账。心跳恢复不能追溯接收旧围栏下的迟到结果。

## 7. 审批凭据

`cls=external` 的任务只有在中枢验证审批凭据后才能派发。审批凭据至少绑定：

- `credential_id` 与 `approval_record_id`；
- `task_id` 与规范化信封的 `envelope_sha256`；
- 具体动作范围、审批角色、决定时间、失效时间和一次性使用标记；
- 中枢账本中的审批事件。

审批凭据只对绑定的信封、动作范围和有效期有效，不得挪用于另一信封、扩大范围或变成长期授权。每次外部动作在执行前必须再次确认凭据未使用、未过期且信封摘要一致。

为避免摘要与凭据互相包含，`envelope_sha256` 按规范化 JSON 计算的“待审批信封”计算，计算时省略 `approval` 字段；验证时必须使用同一规范化规则重建待审批信封。规范化规则和实际摘要必须由实现测试固定。

审批选项可以包含批准、修改后重报、搁置或取消。只有能够生成本次信封有效凭据的决定才可进入执行；其他结果应终止本次提交或要求新的信封。审批记录中不得存放密钥、访问令牌或明文口令。

## 8. 结果与产物指针

执行结果必须先在执行端持久落盘，再回传指针。每个结果或产物指针包含：

- `uri`：中枢可解析的稳定引用；
- `sha256`：内容 SHA-256，小写十六进制；
- `bytes`：非负整数；
- `media_type`：媒体类型。

中枢接收指针后必须执行存在性、字节数、媒体类型和哈希核验。缺指针、空结果、字节数不符或哈希不匹配都视为未交付，不得把口头描述当作结果。

传输实现可以重试，但相同 `(task_id, attempt, result_kind)` 只能形成一个已确认结果。迟到结果仍须核对围栏；旧围栏结果只进入审计和隔离区。

## 9. 操作账义务

接口只要做出影响外部世界的动作，包括发送消息、改动持久数据、调用外部服务或改变可见资源，就必须在本地追加操作账。

每条操作账至少包含：

`operation_id`、`task_id`、`attempt`、`fence`、`occurred_at`、`action_class`、`action`、`target_digest`、`outcome`、`result_ref`、`trace_id`。

对外动作应当采用两阶段记录：

1. 动作前追加 `intent`，固定任务、围栏、动作类别和目标摘要。
2. 动作后追加 `confirmed` 或 `failed`；进程中断则恢复时追加 `unknown`。

操作账必须追加式保存，不包含密钥、令牌、明文口令或不必要的目标原文。操作账、连接日志、中枢事件账本应能通过任务号、尝试号、围栏和追踪号相互印证。

抽样核对时找不到相应操作账的外部动作按没有证据处理；`unknown` 记录不得自动重试，必须先由核验者或负责人确认实际副作用。

## 10. 裁定记录与 canonical 词表

裁定词的唯一 canonical 集合为：

| 值 | 含义 | 下游动作 |
|---|---|---|
| `通过` | 产物、内容和证据都满足要求 | 可报交付 |
| `带注通过` | 已满足交付，但有必须随报的非阻塞注记 | 交付并携带注记 |
| `条件通过` | 交付依赖尚未满足的明确条件 | 条件满足前不得报交付 |
| `不通过` | 未满足验收标准，或发现虚假完成 | 打回重做 |
| `未核` | 尚未完成核验，且未核出口三项齐全 | 按补齐计划继续 |
| `作废` | 任务被取消，或结论建立在已证伪的前提上 | 停止推进，保留完整记录 |

历史值 `驳回` 是 `不通过` 的只读别名。读取历史记录时，先把 `驳回` 归一化为 `不通过`，再按 canonical schema 验证。任何新写入、事件、API 响应、导出文件、命令输出或面向人的交付只许使用六个 canonical 值；`驳回` 出现在产出路径时必须拒绝。

每份裁定记录至少包含：

- `verdict_id`、`task_id`、`verdict`、`decided_by_role`、`decided_at`；
- `basis.deterministic_check`：程序核验产物存在性、大小、哈希与格式；
- `basis.independent_verification`：未参与执行的核验者复查内容，自检必须显式标注；
- `basis.physical_readback`：按证据形态回读原件或实际界面；
- 证据指针与操作账引用。

状态特定要求：

- `带注通过` 必须至少有一条非空注记。
- `条件通过` 必须写明负责人、条件列表和满足期限；条件满足前不得报交付。
- `未核` 必须同时写明负责人、一个可执行的最小补齐动作和绝对补齐时限；三项缺任一项时，该结论按 `不通过` 处理。
- `不通过` 和 `作废` 必须带可审计原因；`作废` 还要保留已发生工作的关联引用。

裁定与执行状态分开保存。执行者的 `completed` 事件、心跳持续或结果文件存在，都不能单独形成 `通过`。

## 11. 幂等、顺序与错误处理

- 任务提交按提交主体与 `idempotency_key` 去重；语义冲突必须报错。
- 事件按 `(task_id, seq)` 去重；执行端按任务、尝试和围栏避免重复副作用。
- 审批凭据一次性消费；同一凭据不得触发第二个外部动作。
- 结果按任务、尝试和结果类别去重，但不同类别的结果不能互相覆盖。
- 旧围栏消息、重复消息、缺号消息、毒消息、未知任务和完整性失败都必须形成审计记录，不得静默丢弃。
- 可重试错误进入有界重试或新任务；不可重试错误进入死信；副作用未知进入人工处置。

## 12. 最低一致性要求

实现满足本契约时，至少证明以下行为：

1. 无效信封在执行和成功入账之前被拒绝。
2. 相同幂等键和相同语义只产生一个任务；不同语义产生冲突。
3. 重复投递和补投不产生第二次执行或第二次外部副作用。
4. 租约回收后旧围栏结果被拒，新围栏拥有唯一写入资格。
5. 同资源任务串行，不同资源可以并发。
6. 外部动作缺少有效审批时不执行。
7. 历史 `驳回` 只在读取边界归一化为 `不通过`，所有产出拒绝 `驳回`。
8. 产物指针和 SHA-256 可回读；任何不一致都判未交付。
9. 裁定记录与执行状态分账，且裁定只写 canonical 六值。
10. 对外动作的操作账可被关联核对，`unknown` 不自动重试。

`tests/conformance/` 提供机器可重复的最低样例。附加实现的测试可以更严格，但不得放宽本文件或 schema 的约束。
